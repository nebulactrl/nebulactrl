# Coverage targets, measurement and gates: what comparable projects do

Question: NebulaCtrl wants a 90% coverage target and a gate on it. Today it reports 74.6% overall in Codecov (Go 71% per package, web 89%), informational only. Should it add `-coverpkg=./...`, coverage from the smoke binaries (`go build -cover` + `GOCOVERDIR`), exclusions, and a required Codecov status?

Primary sources only: [Go integration-coverage blog](https://go.dev/blog/integration-test-coverage), [go.dev/doc/build-cover](https://go.dev/doc/build-cover), `go help testflag` and the `cmd/go` and `cmd/cover` source of go1.27.3, [Go 1.22 notes](https://go.dev/doc/go1.22), the [Google Testing Blog post](https://testing.googleblog.com/2020/08/code-coverage-best-practices.html), [Codecov docs](https://docs.codecov.com/docs/commit-status), [Bun](https://bun.sh/docs/test/code-coverage), and each project's own config at the pinned commit. Totals are from Codecov's public API on 2026-11-01. NebulaCtrl is read at `24ff4aa`. Anything not read from a primary source says **unverified**; **[INFERENCE]** marks reasoning. A throwaway Go module in `/tmp` was used to check three Go behaviours; no repo build or test was run.

- **Gate at all:** of the 10 rows above, only Jaeger is *known* to require its coverage statuses; otel, Argo CD, etcd, docker/cli and moby have non-informational statuses (required-ness unverified); Mattermost, Vitess, Consul and Woodpecker are informational. [oss-quality-tooling.md](oss-quality-tooling.md) found no coverage service in 11 of its 16 projects (grafana, gitea, traefik, caddy, prometheus, nomad, coder, cli/cli, minio among them), and kubernetes, terraform, cockroach, hugo, cilium, golangci-lint, controller-runtime, cluster-api and cert-manager have no Codecov file at HEAD (a service config elsewhere is unverified). A **minority of Go projects gate at all**.
- **At 90% or above:** exactly two, otel (project 90, patch 95) and Jaeger (95/95). They are also the only two of the sample with totals above 90%. Every project that relies on `target: auto` sits at 30 to 73%: the relative gate stops decline, it does not push up.
- **Relative beats absolute for the rest:** `auto` plus a 1 to 2% threshold is the norm (Argo CD 2, etcd 1, Mattermost 1); docker/cli and moby use 15%, which is a near-switch-off.
- Both 90%+ projects keep the number high structurally. Jaeger fails the build if a package has no `_test.go` and no `.nocover` file with a written reason (`check-test-files.sh`, [Makefile#L147-L159](https://github.com/jaegertracing/jaeger/blob/7bb2d23b1/Makefile#L147-L159)); single-`main.go` packages are exempt.

## 2. Guidance on targets and gate shape

Google Testing Blog, quoted verbatim:
- "at Google we offer the general guidelines of 60% as “acceptable”, 75% as “commendable” and 90% as “exemplary.” However we like to stay away from broad top-down mandates and encourage every team to select the value that makes sense for their business needs."
- "We should not be obsessing on how to get from 90% code coverage to 95%. The gains of increasing code coverage beyond a certain point are logarithmic. But we should be taking concrete steps to get from 30% to 70% and always making sure new code meets our desired threshold."
- "While project wide goals above 90% are most likely not worth it, per-commit coverage goals of 99% are reasonable, and 90% is a good lower threshold. We need to ensure that our tests are not getting worse over time."
- Gate options it lists: "gate on coverage for all code vs gate on coverage to new code only; gate on a specific hard-coded code coverage number vs gate on delta from prior version, specific parts of the code to ignore or focus on." It also warns that the gate can become "a checkbox" and "pressure to 'hit the metric' almost never yields the desired outcome", and that "Any mandate to reach x% code coverage should be accompanied by infrastructure investments to make testing easy".
- On quality: coverage "just guarantees that they have been executed by a test"; "Be mindful of copy/pasting tests just for the sake of increasing coverage". Its remedy is mutation testing.
- On integration tests: the aggregate of unit and integration coverage "is paramount", but "some of the coverage from integration tests and end-to-end tests is incidental and not deliberate".

Codecov mechanics ([commit status](https://docs.codecov.com/docs/commit-status)):
- `target: auto` compares against the base commit; `threshold` allows a drop of N%; `informational: true` makes the status pass "no matter what". Patch status "only measures lines adjusted in the pull request".
- Coverage is `hits / (hits + partial + miss)` over **lines** ([about](https://docs.codecov.com/docs/about-code-coverage)), not Go's statement percentage, so the two numbers differ. Vitess sets `parsers.go.partials_as_hits: true` to soften this.
- **Flakiness of the number.** Codecov's own list of causes of unexpected change ([doc](https://docs.codecov.com/docs/unexpected-coverage-changes)) includes "Failing to upload coverage reports, or a different number of reports between head and base", time-sensitive tests, and "different error handling paths ... oftentimes the root of 'flaky' tests". That is why Argo CD takes a 2% threshold.
- **Silent block.** `codecov.notify.after_n_builds` withholds statuses until N reports arrive ([notifications](https://docs.codecov.com/docs/notifications)). Jaeger's ADR: Codecov withholds "every notification — including the required `codecov/patch` and `codecov/project` statuses ... so drift in that number blocks all merges with no failing check to point at"; they added `check_coverage_uploads.py` to assert the count. NebulaCtrl's `after_n_builds: 4` must move with every added upload.
- Carryforward ([doc](https://docs.codecov.com/docs/carryforward-flags)) fits suites that do not run on every commit; it needs a full first upload and carried flags do not show in PR comments by default.
- Ratchet: `target: auto` with `threshold: 0` is Codecov's built-in ratchet. A fixed `target: 90%` below the current number fails every PR, including docs-only ones.
- Jaeger ([ADR 004](https://github.com/jaegertracing/jaeger/blob/7bb2d23b1/docs/adr/004-migrating-coverage-gating-to-github-actions.md)) moved the project floor into GitHub Actions because Codecov's checks "suffer from latency ... and intermittent rate-limit failures", but kept `codecov/patch` required: "with the total near 97.4% against a 95% floor a pull request can leave a substantial diff uncovered without moving it measurably. ... the project gates catch slow erosion ... `codecov/patch` catches a single diff landing poorly covered code inside the headroom."

## 3. Go specifics

**Per-package versus `-coverpkg`.** `go help testflag`: "The default is for each test to analyze only the package being tested." So an HTTP test in `internal/app` earns nothing for `internal/api`; that is why they read 6%, 21%, 10%. `cmd/go/internal/test/test.go#L884-L925` states the other semantics: with `-coverpkg`, each package's percentage is "a fraction of *all* the statements that match the pattern".
- Who: Woodpecker `-race -cover -coverpkg=./...` for every target including `e2e/...` ([Makefile#L195-L221](https://github.com/woodpecker-ci/woodpecker/blob/65e0cd001/Makefile#L195-L221)); otel (list of all module packages, `-covermode=atomic`); etcd (all non-`tests` modules, unit and integration, `-covermode=set`, merged with gocovmerge: [scripts/test.sh#L287-L331](https://github.com/etcd-io/etcd/blob/1573d5941/scripts/test.sh#L287-L331)); Kubernetes (`-coverpkg k8s.io/...` for instrumented binaries built through `go test -c`, [hack/lib/golang.sh#L765-L780](https://github.com/kubernetes/kubernetes/blob/3c690c189/hack/lib/golang.sh#L765-L780)). Per-package only: Argo CD (`-cover` plus `-test.gocoverdir`, [Makefile#L489](https://github.com/argoproj/argo-cd/blob/2a73dde17/Makefile#L489)), Mattermost (`-coverprofile ... -covermode=atomic`), Jaeger (`./...`, `-cover -covermode=atomic`).
- **Packages without tests.** Verified in go1.27.3: plain `go test -coverprofile ./...` already lists untested packages as 0% (since Go 1.22: "functions in the package are treated as uncovered", [notes](https://go.dev/doc/go1.22)). So per-package numbers already carry the denominator of untested packages; `-coverpkg` is not needed for that.
- **Init-only code.** Verified: a package whose only coverage is `init()` shows `init 0.0%` per package, `100.0%` under `-coverpkg=./...` once any test imports it (even blank). Package-level initialisation code is credited to any test binary that links the package, so a hub test such as `internal/app` raises many packages' init lines. [INFERENCE] small in statements.
- **Incidental credit.** Google's "incidental and not deliberate" applies: `internal/app` tests would now cover `internal/api`, `auth`, `teams` handlers without a deliberate test of each. That is also the legitimate point of integration tests; the discipline is to read uncovered lines, not the percentage.
- **Cost and pitfalls.** (a) `go test -coverprofile` over many packages only concatenates the profiles ([cover.go#L48-L75](https://github.com/golang/go/blob/go1.27.3/src/cmd/go/internal/test/cover.go#L48-L75)); duplicate blocks are merged afterwards (`go tool cover`: set mode ORs, count mode adds, [profile.go#L91-L108](https://github.com/golang/go/blob/go1.27.3/src/cmd/vendor/golang.org/x/tools/cover/profile.go#L91-L108)), and Codecov says "We always merge the data" ([merging](https://docs.codecov.com/docs/merging-reports)); the exact line-merge rule is **unverified**. (b) The covered set is selected from the closure of the packages given to that `go test` call (`SelectCoverPackages(plist...)`, [test.go#L884-L887](https://github.com/golang/go/blob/go1.27.3/src/cmd/go/internal/test/test.go#L884-L887)), so shard profiles overlap on shared packages (db, platform) but not each hold the whole repo, and merging by block or line counts no statement twice (read from source, not run on this repo). (c) Every run action depends on one "write coverage meta-data file" action fed by all covered builds, and the test cache key hashes those builds ([test.go#L1814-L1835](https://github.com/golang/go/blob/go1.27.3/src/cmd/go/internal/test/test.go#L1814-L1835)): a change in any covered package invalidates the cache of every test. NebulaCtrl CI already uses `-count=1`; the extra cost is compile and link, **unmeasured**. (d) `-race` forces `atomic`, "significantly more expensive"; modes must match when merging ([Jaeger pins atomic](https://github.com/jaegertracing/jaeger/blob/7bb2d23b1/Makefile#L150-L153), Argo CD uses `covdata merge -pcombine` for mixed modes). (e) Retries: `go test -coverprofile` truncates its file, so `gotestsum --rerun-fails` can leave a one-package profile; Jaeger switched to counter directories for that reason.

**Integration coverage with `go build -cover`.** Go 1.20+: build with `-cover` (main-module packages by default, others via `-coverpkg`), run with `GOCOVERDIR=dir`, then `go tool covdata percent|textfmt|merge -i=dir` ([doc](https://go.dev/doc/build-cover)).
- Who: Argo CD (e2e processes built `-cover`, `GOCOVERDIR` per component, merged with `covdata merge -pcombine`, uploaded as flag `e2e`: [ci-build.yaml#L640-L677](https://github.com/argoproj/argo-cd/blob/2a73dde17/.github/workflows/ci-build.yaml#L640-L677), [Makefile#L181-L185](https://github.com/argoproj/argo-cd/blob/2a73dde17/Makefile#L181-L185)); Jaeger (an instrumented binary spawned by its e2e legs, 15 of 27 uploads); Mattermost documents the older `TestRunMain` wrapper ([main_test.go#L12-L17](https://github.com/mattermost/mattermost/blob/2b3fb21fe/server/cmd/mattermost/main_test.go#L12-L17)). etcd's e2e runs prebuilt binaries where "-cover ... do not have any impact" ([test.sh#L175](https://github.com/etcd-io/etcd/blob/1573d5941/scripts/test.sh#L175)), so etcd counts none.
- **Pitfalls, all documented:** "Programs built with `go build -cover` will only write out complete profile data at the end of execution if the program invokes `os.Exit()` or returns normally from `main.main`" (a panic or signal loses it; `runtime/coverage.WriteCountersDir` is the escape hatch). Argo CD: only 4 of its 6 components report, the others "don't shut down gracefully". Jaeger: stop with SIGTERM, not SIGKILL; do not name the variable `GOCOVERDIR` for a child of `go test` (the toolchain overwrites it); a meta-only directory converts to every statement at zero and "collapses the reported total"; `after_n_builds` must equal the number of uploads that carry coverage.
- **NebulaCtrl-specific:** `tests/integration/main_test.go` says the suite "runs the control plane and an agent in-process", and `tests/run.sh` calls `go test ... ./tests/integration/...`. **[INFERENCE, not run]** Smoke coverage therefore needs no instrumented binary: add `-coverpkg=./... -coverprofile=...` to that `go test`. A binary build would only add `cmd/*` wiring (about 15.5k non-test lines by `wc -l`, scale only) and the real process boundary, at the cost of the pitfalls above.

## 4. Exclusions

| Excluded | Who | Reading |
|---|---|---|
| generated code (`*.pb.go`, `*generated*`, sqlc, parsers) | Argo CD, otel, etcd, Jaeger, vitess (each file with its generator named), docker/cli, NebulaCtrl | legitimate; Mattermost's comment: "they appear in cover.out, but they aren't production code and inflate the denominator" |
| mocks and test helpers (`**/mocks/**`, `storetest`, `testutil`) | Argo CD, Consul, Mattermost, Woodpecker, Jaeger | legitimate |
| test infrastructure, e2e harness, fixtures (`test/**`, `tests/**`, `e2e/**`, `**/fixtures/*.go`, `internal/tools`, examples) | Argo CD, etcd, Woodpecker, Jaeger, vitess | legitimate: not shipped |
| vendored / third-party | Argo CD, Consul, docker/cli, moby, otel | legitimate |
| `**/main.go` only | Jaeger | accepted for thin entry points; Jaeger keeps the rest of `cmd/` measured |
| whole `cmd/` | none seen | would be the gaming case here: `cmd/` holds ~15.5k non-test lines (`wc -l`, scale only) of real wiring |

- Mechanisms: Codecov `ignore` is path or regex only ([doc](https://docs.codecov.com/docs/ignoring-paths); `folder/*` is not recursive, use `folder/**/*`). Go's cover tool has no in-source exclusion marker (none found in `cmd/cover`; [golang/go#31280](https://github.com/golang/go/issues/31280) asks for unreachable-code exclusion and is open). Bun has none either ([oven-sh/bun#7662](https://github.com/oven-sh/bun/issues/7662), open).
- Guidance: Google allows "specific parts of the code to ignore or focus on" and notes "testing debug log lines is often not as important", but decides per review of uncovered lines, not by hiding them. Jaeger's discipline is the model: an exemption needs a written reason (`.nocover`), and `FIXME` reasons are highlighted. Rule of thumb: exclude by what the code *is* (generated, harness, vendored), never by how well it is tested.

## 5. TypeScript and Bun

- Bun: "Coverage only tracks files that are loaded" ([troubleshooting](https://bun.sh/docs/test/code-coverage)); the default excludes `node_modules`, non-JS loaders and test files. There is no include option: [oven-sh/bun#15840](https://github.com/oven-sh/bun/pull/15840) (`coverageInclude`) is an open, unmerged PR. Jest has `collectCoverageFrom` ("even if no tests exist for this file and it's never required"); Vitest's `coverage.include` defaults to "files that were imported during test run".
- So NebulaCtrl's 89% for `apps/web` is lines in loaded files; unloaded files are absent from `lcov.info` and, **[INFERENCE]**, from Codecov too. There are 1036 non-test `.ts/.tsx` files and 200 test files under `apps/web/src` (`find`, includes generated files that `codecov.yml` ignores). Measure the gap: diff `SF:` lines of `lcov.info` against `git ls-files 'apps/web/src/**/*.ts*'` minus the ignore list.
- `coverageThreshold` in `bunfig.toml` ("exits with a non-zero exit code") is not enforced when only `--coverage-reporter=lcov` runs ([doc](https://bun.sh/docs/test/code-coverage), [oven-sh/bun#32118](https://github.com/oven-sh/bun/issues/32118)). `ci.yml` passes lcov only, so add `text` if Bun's own threshold is used. There is no `bunfig.toml` in the repo today.
- Bun's own text: "80%+ overall coverage: Generally considered good ... Lower coverage for UI components: Often acceptable".

## Recommendation for NebulaCtrl

**Measure (one PR, still informational; then read the new baseline before choosing numbers):**
1. **`-coverpkg=./...`: yes**, in the three Go shards and in `tests/run.sh`. It matches Woodpecker, otel, etcd and Kubernetes, and credits `internal/app` HTTP tests to `api`, `auth`, `teams`. Cost: more compile and link per shard, **unmeasured**; run one shard before and after. Use `-covermode=set` (the default without `-race`). Keep Codecov flags `go` and `web`.
2. **Smoke coverage: yes, in-process only.** Add `-coverpkg=./... -coverprofile` to the smoke and full `go test` calls and upload as flag `smoke` (and `full` when it runs, `carryforward: true`). Bump `after_n_builds` from 4 to 5 for the always-present smoke upload (Jaeger's lesson: keep it equal to the uploads that carry coverage; how Codecov counts carried-forward flags toward N is **unverified**). **Not now: `go build -cover` binaries.** The harness is already in-process; the binary route only adds `cmd/*`, needs graceful SIGTERM exit from agent and server, and has the pitfalls above. Revisit only if `cmd/` stays uncovered after step 3.
3. **Exclusions:** keep the current generated-code list; add `tools/**`, `tests/fixtures/**`, `tests/install/**` (harness and dev tooling, same class as Jaeger's `internal/tools`, Argo's `test/**`, Woodpecker's fixtures) and the test-support packages `scripts/ci/deadcode.sh` already defines (`SUPPORT_RE`: `internal/testutil/`, `internal/templates/testsample/`, `internal/**/<name>test/`), written as Codecov globs and checked with the validator. Add `**/main.go` only for thin entry points. Do not exclude `cmd/**` or product packages to reach 90.
4. **Web:** measure the unloaded-file gap first. If it is material there is no clean fix today (no `coverageInclude`): either a dedicated test that imports the missing modules (it gives incidental credit) or accept 89% as an upper bound and say so next to the number.

**Gate (two stages, solo-maintainer friendly):**
- **Now:** `patch` `target: 90%`, `only_pulls: true`, **required**; this is Google's "90% is a good lower threshold" for per-commit coverage and starts working on day one. `project` `target: auto`, `threshold: 1%` (etcd, Mattermost, Argo CD 2%) as the ratchet, required or informational as you prefer. Do not set `project: 90%` yet: at 74.6% it fails every PR, and Google says "project wide goals above 90% are most likely not worth it".
- **Later:** once the measured total has held at 88% or more for a few weeks, set `project` `target: 90%`, `threshold: 1%` (only otel and Jaeger do this and both sit at 91 to 99%). Write down that 90% is a floor with jitter, not a goal to push past (Google: 90 to 95 is logarithmic).
- **Make the gate cheap to live with.** Required Codecov means a Codecov outage or upload miss blocks merges (Jaeger's reason for an in-repo gate). Options: keep `fail_ci_if_error: false` and use admin bypass, or add a small in-repo floor (`go tool cover -func` total, or `go tool covdata percent`) beside the Codecov patch gate, as Jaeger did. For a solo maintainer, start with Codecov patch only.

**Reaching 90% realistically.** [INFERENCE: baseline after steps 1 to 3 unknown; get it before committing.]
- Free points first: `-coverpkg` credit, smoke credit and exclusions may close part of the gap without new tests; the number is unknown until one CI run.
- Then sort uncovered statements per package (`go tool cover -func`, descending by uncovered count, not by percentage) and fund the largest few. With ~127k Go lines, one point is on the order of 1.3k lines (rough, lines not statements), so closing 15 points by hand is a large project (effort unmeasured); the patch gate stops it growing, and Google's "boy-scout rule" does the rest.
- Trade-offs: `-coverpkg` raises the number partly by incidental coverage (Google's warning), so keep reviewing uncovered lines in the patch view; a required 90% patch gate adds friction to small fixes (the only bypass is an admin merge); chasing the project number past ~90% buys little. A realistic end state: patch 90% required, project ratchet 1%, project target 90% once reached. If it stalls at ~85%, hold there rather than excluding code.
